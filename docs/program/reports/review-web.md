## Done first: what review-backend.md asks of trooth-web

1. **Recalls screen** (`/dashboard/semanto/recalls`; `components/dashboard/semanto/recalls.tsx`, `lib/semanto-recalls.ts`, `app/dashboard/semanto/recalls/{page,loading}.tsx`, sidebar and settings-list entries). The list shows each recall newest first: the statement's first sentence (the title the feed carries, computed as the Worker computes it), what buyers must do, the products (SKU, GTIN, lots or "Every lot"), the notice and authority links (http(s) only), and the feed state from `event`: In the feed (with when), Being sent (attempts; the list is read again every 15 seconds only while one is being sent), Not in the feed (with the Worker's reason), Not sent (`event: null`). Publish is either the form signed with the signing passkey (custody hosted: `POST recalls/options { notice }`, then `POST recalls { notice, assertion }` with the same object, so the challenge's binding holds) or a JWS the company signed (custody customer, the default for that custody; the form says Trooth cannot sign for it). The form checks every Worker rule beside its field before anything is sent (at least one SKU or GTIN, GS1 check digit, action, statement up to the 1000 characters worker-f takes, https notice address, announced date not in the future, an authority with its page or not at all, list lengths), moves focus to the first field to fix, and shows the title agents will see. A Review step, which takes focus, lists what goes out and says: "Publishing a recall is public and lasting. Anyone who checks your products, and every AI agent reading your changes feed, sees it, and it cannot be taken back. When the recall ends, publish a new notice that says so." Back keeps the form. Success says where the recall is; `signature_invalid` (422) says nothing was published and shows the Worker's reason; a passkey that did not finish, a browser without passkeys, and no signing passkey yet (Add a signing passkey first) each have their own words. Send again on a recall that did not reach the feed rebuilds the notice from the row's own fields (same recall id) and stores it again after one passkey, which the Worker's `reviveRecallEvent` sends; a customer-held key is told to upload the same signed file. Loading, empty ("No recalls published", with the next step), error with Try again and request id, and off states come from the shared `ScreenRead`.
   Reference flows: the CPSC business portal on SaferProducts.gov (product, hazard and remedy in order, then Review & Submission, then a plain submitted screen: https://cpsc.gov/Business--Manufacturing/Recall-Guidance/How-to-Conduct-a-Recall/Filing-an-Online-Initial-Section-15b-Report, https://www.saferproducts.gov/business); Google Merchant Center's "Recalled product" item state with what to do next shown beside the product (https://support.google.com/merchants/answer/15075346); Shopify's per-item product status shown and filterable in the product list (https://shopify.dev/changelog/use-product-statuses-to-filter-and-manage-products).
2. **Write-back send**: the changes and a new `idempotency_key` are frozen when the person presses Review; a retried click of that Send carries the same key with the same items (the Worker answers the same run); a new Review is a new send with a new key. The 409 for a key reused with other items is recognised (`isKeyReused`) and worded: "Nothing was sent: the key this send carried had already been used for other changes. Press Send to send these changes as a new send." The next press carries a new key.
3. **Alert confirmation return**: `reason=link_expired` ("That confirmation link has expired: each one works for 24 hours.") and `reason=link_invalid` ("That confirmation link does not work any more. It was used already, or a newer link replaced it.") are worded apart, each with "Resend to <address>" buttons for every pending address right in the message (or, with none pending, how to add the address again).
4. **Recent changes**: words for every action the Worker writes (read from `src/os/*.ts` audit calls and `src/serve/os-routes.ts` record calls): `settings.save`, `keys.rotation.start|confirm|cancel`, `keys.revoke`, `keys.rotate`, `passkeys.add`, `versions.sign`, `versions.approve`, `versions.withdraw`, `connectors.add|create|revoke`, `connectors.uninstall.uninstalled|disconnected|shop_redact`, `connect.approve|deny`, `google.connect.start`, `google.connect`, `google.reconnect`, `google.disconnect`, `company.signing_policy`, `company.surfaces.add|remove`, `company.alerts.add|resend|remove|confirm`, `writeback.send|retry`, `sellers.list`, `recalls.publish`. An action the page does not know reads "made a change", never its id. Roles are words (Owner, Admin, Member, Viewer, App, From the confirmation email), a connector's `connector:<kid>` reads "An app, with its connector key", and internal targets (`delivery`, `signing_policy`, `google`) are left out.
5. **Additive members**: `advice` (shown as "Next:" under a connector test that is not connected), `resend_available_at` (Resend disabled with "Resend at <time>" and a line saying when it opens; one timeout to that moment, nothing ticking; a 429 from another tab is said as the same wait using `retry_after`), `next_version` (the seller list's new version and the upload check), `counts` (run summary and history), `rotation.dns_record` (the new key's TXT record after a reload, replacing a string-replacement guess). `interval` was considered and not used: the approve page does not poll (the app server does), so nothing on screen needs it. Approving twice answers 200 and the page already treats that as approved (and a double click sends once).
6. **Recall allowlist**: exactly the three paths, held by `tests/semanto-api.test.mjs` (each allowed with its method; `GET recalls/options`, `POST recalls/<id>`, `GET recalls/<id>`, `POST recalls/options/again`, `GET recalls.csv`, `POST recall` refused).

## Findings

Severity, place, repro (before), fix, guard.

### High

1. **No way to publish a recall.** Requirement 24 had a write path in the Worker but no screen. Repro: no route under `/dashboard/semanto` reached `POST recalls`. Fixed: the Recalls screen above. Guards: `tests/semanto-review-web.test.mjs` (recall form, notice, upload, GTIN tests), `tests/semanto-api.test.mjs` (allowlist), QA states `recalls`, `recalls-send-again`, `recalls-build-invalid`, `recalls-review`, `recalls-published`, `recalls-upload`, `recalls-upload-review`, `recalls-upload-refused`, `recalls-customer`, `recalls-empty`.

### Medium

2. **Write-back could send different items under a used key.** `components/dashboard/semanto/writeback.tsx`: the key was made at Review but the items sent were recomputed on each render from the preview, which SWR revalidates on focus. Repro: Review two changes, switch tabs while the preview drops one, press Send: other items with the same key, which the Worker now refuses with an unworded 409. Fixed: Review freezes the items and the key; the 409 is worded and the next press is a new send. Guard: unit test "write-back: a new key per send"; QA `writeback-key-reused` (two sends, same items, different keys) and `writeback-new-send`.
3. **Recent changes showed raw action ids.** `company-settings.tsx`: the select fell back to `{raw}`, and `passkeys.add`, `versions.*` and `recalls.publish` had no words; roles printed as `owner`, `connector`, `public`; `connector:<kid>` printed raw. Fixed as above. Guard: unit test "recent changes: every audit action"; QA `company` fails on any raw id.
4. **Resend ignored the Worker's wait.** The page kept a 60-second wait only for sends from the same tab; after a reload Resend was on and answered 429 as an error. Fixed: `resend_available_at` and `retry_after`. Guard: QA `company-resend-wait`, `company-resend-429`.
5. **A confirmation link that did not work left no direct way out.** Both reasons ended "Resend it from the list below", the invalid one did not say a newer link replaces an older one, and the message sat apart from the addresses. Fixed as above. Guard: unit test "the alert confirmation return"; QA `company-alert-expired`, `company-alert-invalid-link` (Resend sends `{ resend }`).
6. **Worker URLs opened unchecked on the guide pages.** `review-sign.tsx` (`f.source_url`, twice), `read-receipt.tsx` (left-out page addresses), `watch-report.tsx` (`c.evidence_url`) put Worker strings in `href`, so a `javascript:` value would run on click. Fixed: `safeHttpUrl` on each; a value that fails is shown as text, not linked. Guard: unit test "the guide pages open addresses from the Worker only as http or https".
7. **Fixtures disagreed with the Worker, so the browser runs proved the wrong shapes.** `scripts/qa-semanto-screens.mjs` answered: the connect request as `semanto.connect_session` without `kid`; host detection in a long form the Worker never answers; previews without `sendable`/`target`; run lists with item fields the Worker leaves out and no `counts`; runs without `counts`/`target`; seller lists without `next_version`/`custody`; connector tests without `advice`; pending alerts without `resend_available_at`; started rotations without `dns_record`; three Google scopes (the Worker answers four) with other purposes; a pasted key's kid "pasted". Each now matches `src/os/*.ts`. Guard: the QA run (its assertions read the corrected members).
8. **A failure caused by the Google connection showed the Worker's marker.** `writeback.tsx` printed `last_error` as "Google said: needs_reconnect: <sentence>" (and "Google said: Google refused this change (400): <message>"). Fixed: "Why: <the Worker's words>", the `needs_reconnect:` marker stripped and a Reconnect Google link added. Guard: QA `writeback-older-run`, and `writeback-run` reads the Worker's real wording.
