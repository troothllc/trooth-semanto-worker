# Program contract, 23 October 2026

The one definition every area builds against. The Semanto Worker implements it; trooth-web calls it through its catch-all proxy route under `app/api/semanto/` (signed-in only, allowlisted, GET and POST only); the Shopify app and worker-f call the parts named for them. If an area must change a shape, it changes this file in the same change and says so in its report.

Conventions (existing, keep them): every `/os/semanto/{trooth_id}/<route>` route uses `workspaceFor` (worker-f session, role owner, admin, member or viewer), JSON bodies capped at 5 MB, RFC 9457 problems from `src/serve/errors.ts`, signed responses through `send`. Roles: `mayAdminister` (owner, admin) for every write below unless stated; `mayOperate` for read-only actions that cost work. Rate limits: the RateLimitDO route groups in `src/readers/rate-limit.ts`; add a group `os_write` (30 a minute per session subject) for the new writes and `public_connect` (10 a minute per address) for the public connect routes. Audit: every write below appends one row to a new `semanto_audit` table (who, role, action, target, before hash, after hash, request id, at) and the dashboard shows it on the company settings screen as "Recent changes".

Down migrations live in `migrations-down/NNNN_name.down.sql` (outside wrangler's `migrations/` folder so they are never applied by accident). Every new up file has one.

## 1a. Delivery settings (exists; extend)

- `GET /os/semanto/{id}/settings` and `POST /os/semanto/{id}/settings` exist (`src/settings/delivery.ts`). Keep them. Add `POST /os/semanto/{id}/settings/preview` that takes the same body and answers `{ object: "semanto.settings_preview", issues, effects: [{ route, before, after }] }` without saving, so the screen shows what a change does before Save. Save writes an audit row.

## 1b. Signing key, domain binding, safe rotation

- `GET /os/semanto/{id}/keys` (exists): add to each key `state` = `active | next | retiring | revoked | expired`, `overlap_until`, `created_at`, and to the body `binding: { dns_name, dns_value, found: boolean, checked_at }` and `rotation: null | { rotation_id, next_kid, current_kid, overlap_until, state: "started" | "confirmed" | "completed" | "cancelled" }`.
- Rotation becomes staged (GitHub deploy keys, AWS KMS, Stripe API key roll):
  - `POST /os/semanto/{id}/keys/rotation/start` `{ custody: "hosted" }` or `{ custody: "customer", public_jwk }` → new key in state `next`, published in the JWKS at once (so verifiers learn it), not yet used to sign. Answer includes `dns_record` for the new kid. For custody customer the dashboard generates the pair in the browser (WebCrypto Ed25519), sends only the public JWK, and shows the private JWK once with Copy and Download, then forgets it.
  - `POST /os/semanto/{id}/keys/rotation/confirm` `{ rotation_id, passkey assertion as in sign }` → `next` becomes `active`, the old key becomes `retiring` with `overlap_until` = now + ROTATION_OVERLAP_MS. Signing uses the new key from here.
  - `POST /os/semanto/{id}/keys/rotation/cancel` `{ rotation_id }` → only before confirm; the `next` key is revoked.
  - `POST /os/semanto/{id}/keys/{kid}/revoke` (exists) → typed confirmation `{ confirm: "<kid>" }` required; refuses to revoke the only active key; a revoked key goes on the revocation list at once.
  - Overlap end needs no cron: a `retiring` key whose `overlap_until` has passed reads as `expired` wherever keys are read (computed on read).
- `POST /os/semanto/{id}/keys/binding/check` → looks up the DNS TXT record now (existing DNS helper in `src/setup/`) and answers the `binding` object.
- The old `POST /os/semanto/{id}/keys/rotate` stays as start plus confirm in one call for API users; the dashboard uses the staged routes.

## 1c. Read receipts

- `GET /os/semanto/{id}/receipts` (exists, digest by day) gains query filters: `from`, `to` (YYYY-MM-DD, at most 92 days apart), `agent` (operator name), `path` (prefix), `status` (`signed_agent | unsigned`), `cursor`, `limit` (1 to 200). Answer `{ object: "semanto.receipts", rows: [{ day, agent, operator, path, reads, signed: boolean, last_at }], totals: { reads, agents, paths }, agents: [names for the filter list], next_cursor }`.
- `GET /os/semanto/{id}/receipts.csv` (exists) takes the same filters and streams the same rows. Header row fixed. Cells that start with `= + - @` are prefixed with a single quote (CSV injection).

## 1d. Connector keys

- `GET /os/semanto/{id}/connectors` → `{ object: "semanto.connectors", keys: [{ kid, source, label, created_at, last_used_at, revoked_at }] }`.
- `POST /os/semanto/{id}/connectors` (exists, paste a public JWK) gains `label` and validation answers that name the exact problem (not JSON, not Ed25519, private parts present, duplicate kid).
- `POST /os/semanto/{id}/connectors/create` `{ source, label }` → the Worker makes an Ed25519 pair, stores the public key, answers the private JWK once (`secret_shown_once: true`). Never logged, never stored.
- `POST /os/semanto/{id}/connectors/{kid}/test` → the Worker sends a signed challenge round trip: it answers `{ object: "semanto.connector_test", kid, last_signed_request_at, last_result, verdict: "connected" | "never_seen" | "signature_failed" | "revoked" }` from the connector's last signed request (stored per kid on every `commerce/catalog` call: time, result) and, for a key whose source is an edge adapter, fetches `https://{domain}/.well-known/trooth-semanto-connector` (SSRF guard) where the adapter answers its kid.
- `POST /os/semanto/{id}/connectors/{kid}/revoke` `{ confirm: "<kid>" }`.
- Public connect flow for app installs (Shopify first; Stripe CLI and GitHub device-flow pattern):
  - `POST /public/semanto/connect/sessions` `{ app: "shopify", account: "<shop>.myshopify.com", public_jwk, return_url? }` → `{ session_id, poll_token, approve_url: "https://trooth.co/dashboard/semanto/connect/{session_id}", expires_at (15 minutes) }`. Rate group `public_connect`.
  - `GET /public/semanto/connect/sessions/{session_id}` with `Authorization: Bearer {poll_token}` → `{ state: "pending" | "approved" | "denied" | "withdrawn" | "expired", trooth_id?, kid? }`; `withdrawn` is a request the app took back (its signed uninstall or Disconnect arrived before anyone decided), never shown as denied. Polled only by the app server, only while a merchant is on the connect screen (every 2 seconds, stops at expiry).
  - `GET /os/semanto/connect/{session_id}` (session only, no trooth_id) → what the approve page shows: app, account, requested at, state, the app's return address, the caller's companies.
  - `POST /os/semanto/{id}/connect/{session_id}/approve` and `/deny` → approve registers the public key as a connector key with `source = "shopify:<shop>"`. Either on a withdrawn request is a 409 `connect_session_withdrawn` that says the store withdrew it.

## 1e. Connect Google (Merchant Center and Business Profile)

- `GET /os/semanto/{id}/google` → `{ object: "semanto.google", state: "not_connected" | "connected" | "needs_reconnect", account_email, scopes: [{ scope, purpose, granted }], merchant_accounts: [{ id, name }], business_locations: [{ name, title }], connected_at, last_refresh_at, last_error }`.
- `POST /os/semanto/{id}/google/connect` `{ products: ["merchant", "business"] }` → `{ authorization_url }` (authorization code with PKCE, `access_type=offline`, `prompt=consent`, `include_granted_scopes=true`, state bound to trooth_id, user and a 10-minute expiry, stored in D1). Scopes: `https://www.googleapis.com/auth/content` for Merchant, `https://www.googleapis.com/auth/business.manage` for Business Profile, plus `openid email`.
- `GET /public/semanto/google/callback` (public, Google redirects here) → checks state, exchanges the code, seals the refresh token (AES-256-GCM, `src/db/key-seal.ts`, context `google-refresh`), records granted scopes, redirects to `https://trooth.co/dashboard/semanto/connections?google=connected` or `?google=error&reason=<code>`.
- `POST /os/semanto/{id}/google/disconnect` `{ confirm: true }` → revokes at `https://oauth2.googleapis.com/revoke`, deletes the sealed token.
- Refresh: on use only (no cron). A refresh answering `invalid_grant` sets `needs_reconnect`, sends one alert to the alert addresses and the screen shows Reconnect.
- Env: `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` (secret), `GOOGLE_OAUTH_REDIRECT_URI` (var, default `https://api.trooth.co/public/semanto/google/callback`).
- Merchant writes use the Merchant API (`merchantapi.googleapis.com`), not the Content API for Shopping (its sunset is announced for 2026).

## 2. Company settings

- `GET /os/semanto/{id}/company` → `{ object: "semanto.company_settings", signing_policy: { officers_required: 1 | 2 }, surfaces: [{ kind: "website" | "merchant_center" | "business_profile" | "marketplace" | "app", id, label, url?, connected: boolean }], alert_addresses: [{ address, state: "pending" | "confirmed", added_at, confirmed_at }], recent_changes: [audit rows, newest 20] }`.
- `POST /os/semanto/{id}/company/signing-policy` `{ officers_required, confirm? }` → going from 2 to 1 is destructive: needs `confirm: "one officer"` and an owner role, and is refused while a version waits for a second officer.
- `POST /os/semanto/{id}/company/surfaces` `{ add?: surface, remove?: id, confirm? }` → removing a connected surface needs `confirm: <id>`.
- `POST /os/semanto/{id}/company/alerts` `{ add: address }` → stored `pending`, a confirmation email (Resend) with a single-use 24-hour link `GET /public/semanto/alerts/confirm?token=<token>` (token hashed at rest); `{ remove: address, confirm: address }`; `{ resend: address }` at most once a minute. Alerts go only to `confirmed` addresses. Without RESEND_API_KEY the add answers a clear 409.

## 3. Google write-back that sends

- `GET /os/semanto/{id}/writeback` (exists, preview) gains `item_id` per proposed change.
- `POST /os/semanto/{id}/writeback/send` `{ item_ids: ["<item_id>"], confirm: true, idempotency_key }` → creates a run (`semanto_writeback_runs`, `semanto_writeback_items`), enqueues one queue message per item (`kind: "writeback"`), answers `{ run_id, items: [{ item_id, state: "queued" }] }`. The same idempotency key answers the same run.
- Queue consumer: sends through the Google connection; on 429 or 5xx retries with backoff (queue `retry({ delaySeconds })`: 30, 120, 600) up to the queue's attempts; on 4xx marks failed with Google's message in plain words; on `invalid_grant` marks failed `needs_reconnect`.
- `GET /os/semanto/{id}/writeback/runs` and `/writeback/runs/{run_id}` → history with per-item state `queued | sending | sent | failed | retrying`, attempts, last_error, sent_at. `POST /os/semanto/{id}/writeback/runs/{run_id}/retry` `{ item_ids }` retries failed items.

## 4. Seller lists

- `POST /os/semanto/{id}/sellers/lists` either `{ jws }` (custody customer: a compact JWS, `typ` from `JWS_TYPES` sellerList, payload `{ trooth_id, version, issued_at, sellers: [{ seller_id, name, domain?, marketplace?, authorized_from, authorized_until? }] }`) or `{ draft: payload, passkey assertion }` (custody hosted: the server signs after the passkey check, as version signing does). Checked against the company's key valid at `issued_at`; a bad signature answers `422 seller_list_signature` and stores nothing. Versions increase; a lower or equal version is refused.
- `GET /os/semanto/{id}/sellers/lists` → versions with state `valid | superseded | invalid`.
- The public `GET /public/semanto/{id}/sellers` and the authorization check read the newest valid list only.

## 5. Recalls into worker-f's changes feed

- When a recall is stored or changed (`src/commerce/recalls.ts`), the Semanto Worker sends `POST https://os/internal/semanto/recall-events` to worker-f through the `TROOTH_OS` binding (the URL host must be `os`: worker-f answers 404 to `/internal/*` on any other host), `content-type: application/json`, body `{ event_id, trooth_id, os_company_id, domain, recall: { recall_id, product_record_id, gtin?, title, hazard?, remedy?, published_at, source_url?, provenance } , emitted_at }`, header `Trooth-Event-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "t.body">` with secret `SEMANTO_EVENTS_SECRET` (set on both Workers), five-minute tolerance. `event_id` = sha256(trooth_id, recall_id, content hash), 64 lowercase hex, so a repeat is a no-op. A failed send is retried through the queue (`kind: "recall_event"`).
  - Changed by item 5 (worker-f): `domain` added, required. It is the company's proven domain (`semanto_companies.domain`, `domain_proven_at` set); the public MCP feed shows the recall on the published record whose domain equals it. Field limits worker-f checks: ids 1 to 128 of `A-Za-z0-9_.:-`; `gtin` 8, 12, 13 or 14 digits or null; `title` 1 to 300 characters; `hazard`, `remedy` at most 1000 or null; `published_at`, `emitted_at` ISO 8601 UTC; `source_url` https or null; `provenance` one of witnessed, public_record, attested, declared. Body at most 64 KiB.
- worker-f stores the event as a change in the company changes feed (ordered by its own sequence, cursor stable). Answers: 201 `{ object: "semanto.recall_event", duplicate: false, event_id, sequence }` when stored; 200 with `duplicate: true` and the stored sequence for a repeated `event_id`; 401 `invalid_signature` or `signature_expired`; 400 `bad_json` or `bad_request` with `issues`; 413; 415; 429 (120 events a minute per `os_company_id`, `retry-after: 60`); 503 `not_configured` without `SEMANTO_EVENTS_SECRET`. The sender treats any 2xx as delivered and retries 429 and 5xx; 4xx other than 429 is a bug in the event and is not retried.
- Feeds that carry it: `GET /v1/facts/changes?cursor=&limit=` (workspace credential, `facts:read`): `recalls` (oldest first, after `cursor`), `next_cursor` (never null), `has_more`; and the MCP tool `trooth_company_changes` (`recall_cursor` in, `changes.recalls`, `changes.recall_cursor`, `changes.recalls_more` out). Each item is `{ kind: "recall", sequence, event_id, trooth_id, recall_id, product_record_id, gtin, title, hazard, remedy, published_at, source_url, provenance, emitted_at, recorded_at }`.

## 6. C2PA credentials in jobs

- Trigger points: (a) compile, for each image and PDF the build fetched (`src/compiler`), a queue message `kind: "credential"` per asset; (b) write-back send, for each image link sent. The job builds the credential with `src/c2pa/bridge.ts`, stores the manifest in R2 under `credentials/{trooth_id}/{sha256}.c2pa`, records `semanto_credentials (trooth_id, asset_url, sha256, kind, state: "made" | "failed" | "skipped", reason, made_at)`.
- `GET /os/semanto/{id}/credentials?state=&cursor=` → rows plus totals. Public `GET /public/semanto/{id}/credentials/{sha256}` serves the manifest.

## 7. Shopify app

- Lives in `trooth-semanto-worker/apps/shopify` with its own package and tests. Uses the connect flow in 1d (no Trooth credentials typed into Shopify). After approval it: posts the catalog to `POST /os/semanto/{id}/commerce/catalog` signed with its key (RFC 9421, tag trooth-connector) on install and on product webhooks; offers the app embed that adds the head tag (theme app extension, merchant activates through the deep link). GDPR webhooks: `customers/data_request`, `customers/redact`, `shop/redact`; `app/uninstalled` revokes the connector key through `POST /public/semanto/connect/uninstall` signed with the app's key.

## Settled by the Worker backend area (23 October 2026)

The Worker implements every section above and the dashboard shapes just above (docs/spec/os-api.md has every route with example bodies; docs/program/reports/worker-backend.md has the account). Where this file left a choice open, this is what the Worker does; nothing above was removed.

- Passkey requests: `POST keys/rotation/options` `{ rotation_id }` and `POST sellers/lists/options` `{ draft }` answer the sign-options shape with `purpose` and `binding`. `POST sign/options` with `{ purpose: "key_rotation", rotation_id }` or `{ purpose: "seller_list", draft }` answers the same challenge. Confirm needs the assertion when the company's key or the new key is hosted; between two customer-held keys it needs none, as `POST sign` does.
- 1b. `keys/rotation/start` answers `{ object: "semanto.key_rotation", rotation_id, state: "started", custody, next_kid, current_kid, jwks_url, dns_record: { name, value }, overlap_until }`; `overlap_until` there is the date the old key would stop if the rotation were confirmed now, and confirm sets the real one. Confirm answers `{ state: "confirmed", active_kid, retiring_kids, overlap_until }`; cancel answers `{ state: "cancelled", revoked_kid, revocations_url }`. `keys/rotate` (the one-call form) is refused with 409 while a staged rotation is started. `keys/{kid}/revoke` takes `{ confirm: "<kid>", reason?, compromised_at? }`; without `reason` the published reason is "Revoked by the company."; the new key of a started rotation is refused (cancel the rotation instead).
- 1a. `POST settings` answers the `semanto.settings` object of `GET settings`; `detection` is `{ host, at }` from the last host detection or null; `updated_at` is the last save or null. A refused save is the 422 problem `settings_invalid` with `issues`.
- 1c. Rows are ordered newest day first, then most reads. The whole-file reads (the semanto object, llms.txt, facts) have the path `(whole file)`. Without `from` and `to` the last seven days are answered.
- 1d. `source` for a pasted or created key is `edge`, `api` or `app` (`api` when a paste leaves it out); app installs register `<app>:<account>`. The connection test reads the adapter's well-known answer for `edge` keys (adapters/shared/semanto-adapter.mjs serves it when it holds a connector key). `connectors/create` answers 201 `{ object: "semanto.connector_key_created", kid, source, label, public_jwk, private_jwk, secret_shown_once: true }`. Approve or deny of an expired session is 410 `connect_session_expired`; an unknown session is 404 `connect_session_not_found`. `POST /public/semanto/connect/uninstall` takes `{ account? }`, signed with the app's connector key (RFC 9421, tag trooth-connector, a fresh nonce), and answers `{ object: "semanto.connector_revoked", trooth_id, kid, revoked_at }`; a repeat with a new nonce answers the same revocation.
- 1e. The callback's reason codes: `not_configured`, `access_denied` (or Google's own error code), `state_invalid`, `state_expired`, `no_code`, `exchange_failed`, `no_refresh_token`, `scopes_declined`. Disconnect answers the `semanto.google` object with `revoked_at_google`.
- 2. Every `POST company/*` answers the `semanto.company_settings` object. `recent_changes` rows also carry `before_hash` and `after_hash`. A surface `add` may carry `id` (the Worker gives `srf_` plus random bytes when it is left out); a Merchant Center surface takes `data_source` (`accounts/{account}/dataSources/{id}`, needed before products are sent), `content_language` (default en) and `feed_label` (default US); a Business Profile surface's id is the location name (`locations/{id}`). The first of each is the write-back target. The confirmation link redirects to `https://trooth.co/dashboard/semanto/settings?alerts=confirmed` or `?alerts=error&reason=link_invalid|link_expired`. A resend inside the minute is a 429 problem with Retry-After.
- 3. Every preview payload carries `item_id` (a content address, so the same change keeps its id), `sendable` and, when it cannot be sent, `blocked_by`. The Merchant Center http payload is the Merchant API form that is sent: one `productInputs.insert` per product to `https://merchantapi.googleapis.com/products/v1/accounts/{account}/productInputs:insert?dataSource={data source}`; the Business Profile payload is `PATCH https://mybusinessbusinessinformation.googleapis.com/v1/locations/{id}?updateMask={fields}`. Sending a file payload is a 409. Run rows are `{ item_id, connector, target, dry_run, state, attempts, last_error, sent_at }`; `GET writeback/runs` pages 20 runs with `next_cursor`.
- 4. `GET /public/semanto/{id}/sellers` without a query answers the newest valid list `{ object: "semanto.seller_list", trooth_id, version, issued_at, kid, jws, sellers }`; with `domain` (the sku is optional) it answers `{ object: "semanto.seller_authorization", state: "authorized" | "not_listed" | "expired", seller_id?, list_version, brand_trooth_id, seller_domain, checked_at }` from that list (the domain matches a seller's domain, marketplace or seller_id). A company with no list keeps the attestation answer. Submit answers 201 `{ object: "semanto.seller_list", version, state: "valid", kid, issued_at, sellers, custody, jws }`; the list rows also carry `custody`.
- 5. The sender posts to `https://os/internal/semanto/recall-events` with `domain` and `event_id` as 64 lowercase hex. worker-f needs `os_company_id`, a proven domain and `product_record_id`; a recall with none of a matching product record (by sku or GTIN), or a company without a workspace or a proven domain, is kept on this side as a failed event with the reason and is not sent. `title` is the statement's first sentence (at most 300 characters), `remedy` the plain words for the notice's action, `source_url` the authority's page or the notice's, `provenance` public_record with an authority and declared without.
- 6. The stored manifest is `{ object: "semanto.c2pa_manifest", sha256, asset_url, manifest, signing_note }`; the public route serves it signed. Credential rows also carry `source` (`compile` or `writeback`) and, when made, `manifest_url`.

- Follow-ups from the Shopify app area (23 October 2026): rate group `public_connect` counts only `POST /public/semanto/connect/sessions`, 10 a minute per client address; `GET /public/semanto/connect/sessions/{session_id}` is limited by session id (`connect_poll`, 40 a minute, enough for a 2-second poll from shared egress addresses) and `POST /public/semanto/connect/uninstall` by the key id its signature names (`connect_uninstall`, 10 a minute). The uninstall route also serves the app's Disconnect: it takes `{ app?, account?, kid?, trooth_id?, reason? }` with `reason` one of `uninstalled` (the default), `disconnected`, `shop_redact`, recorded in the audit row as the action `connectors.uninstall.<reason>` and answered as `reason`; a well-formed signature by a key never registered is 404 `not_registered`, a bad signature on a registered key stays 401, and a registered key that no app install made is 403. A session's `return_url` must be https on the session's account (`<shop>.myshopify.com`) or `admin.shopify.com`, and approve answers it as `return_url`. On `commerce/catalog`, a product or variant sent with `stock_status: "discontinued"` takes every offer for its sku out (nothing is signed for it; the receipt lists it in `removed`); its product record stays.

## Settled by the backend review (23 October 2026)

docs/program/reports/review-backend.md has the findings and the tests. What a caller notices; nothing above was removed:

- 5. A company stores a recall at `POST /os/semanto/{id}/recalls` (`{ jws }` for custody customer, `{ notice, assertion }` for custody hosted after `POST /os/semanto/{id}/recalls/options` `{ notice }`, or `POST sign/options` with `{ purpose: "recall", notice }`) and lists them at `GET /os/semanto/{id}/recalls`, each with `event: { event_id, state, attempts, last_error, sent_at } | null`, whether it reached worker-f's changes feed. Before this, no route stored a recall, so the sender above never fired. A recall kept as a failed event is sent when it is stored again.
- 1b. `POST keys/rotate` answers 409 for a hosted company asked to move to a customer key (it would skip the passkey the staged confirm asks for); rolling the hosted key and moves between customer keys stay one call. Two rotation starts at once give one started rotation.
- 3. `writeback/send` with an idempotency key already used for other items is a 409 (the same key with the same items still answers the same run). `item_ids` may be left out on send (every sendable change) and on retry (every failed item). Runs carry `counts`. The Google token is sent only to `merchantapi.googleapis.com` and `mybusinessbusinessinformation.googleapis.com`.
- 2. The alert confirmation link answers `reason=link_invalid` for a used, replaced or unknown link and `reason=link_expired` only after 24 hours. Pending alert addresses carry `resend_available_at`.
- Additive members: `interval` on connect session answers, `advice` on the connector test, `next_version` on seller lists, `dns_record` on a started rotation. Approving a session twice for the same company answers the same approval.
- `POST passkeys`, `POST sign` and `POST withdraw` append audit rows (`passkeys.add`, `versions.sign`, `versions.approve`, `versions.withdraw`) and pass os_write.
