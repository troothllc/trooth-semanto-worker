# Setup wizard

Built in `web/semanto/setup/`: the six screens of section 5 against `docs/spec/setup-api.md`, a data client, and a browser harness. The backend was not changed. Nothing was committed.

### Where the build departs from section 5, and why

- **Check my site is pressed, not automatic.** Section 5 has the check start by itself when the install is saved; nothing tells the page when a host saved anything, and the spec's `next_action` is "Check my site". Blue moves from the guide's action to Check my site once the guide's action is used.
- **The three check rows are the API's three** (`markdown`, `signature`, `well_known`). Section 5's first row, "Trooth can reach example.com", is not a separate check in the API; an unreachable site comes back as the markdown check's message ("Trooth could not reach example.com. Is the site online?"). A passing row whose message repeats its label shows "Passed." instead of the words twice.
- **Fix opens guidance, not a field.** The API has no route that edits a fact, and the spec says a wrong fact is fixed on the site, then read again. Fix explains that, links the page and offers Read again.
- **No progress count while checking** ("Checking acme.com: 1 of 3 done" in section 5): the install check is one request, so the page says "Checking acme.com". "Asking 4 AI assistants" drops the 4: the API does not say how many.
- **The alert switch is a sentence.** "Email me when an assistant says something different from my site" has no API field, so the done state says Trooth emails you and does not show a switch that would save nothing.
- **Suggested companies start empty**: the monitoring object has `suggested_questions` but no suggested companies.
- **The passkey offer sits on Screen A** after the email link, so B keeps one blue button.
- **Fastly, Akamai and Gcore are in the Change list** because the API can detect them and a detected host must be able to come back to its guide.
- **"I will do this later"** (asked for in the brief) is on C and saves the step for later with `screen: "C"`.

## What trooth-web still needs

1. **The passkey is now checked by this Worker** (superseded, 2026-10-22). The wizard no longer takes `signing.challenge` or `signing.onAssertion` and no longer falls back to the root hash as a challenge: it asks for `passkeys/options` and `sign/options`, and the sign route checks the assertion before the hosted key is released. See `docs/reports/passkey-signing.md`.
2. **The workspace token.** The client sends `Authorization: Bearer`; `/os` answers allow `https://trooth.co` and `https://www.trooth.co` (and `http://localhost` in development), so the wizard must run on one of those origins with a token trooth-web can read (or behind a trooth-web route that adds it).
3. **The request id across origins.** `Trooth-Request-Id` is not in `EXPOSED_HEADERS` (`src/serve/headers.ts`), so a browser on trooth.co cannot read it; the client falls back to the id the problem's detail names, which only `internal_error` carries. Adding the header to `EXPOSED_HEADERS` is a one-line backend change, not made here.
4. **Sign-in wiring**: `signIn.googleHref`, `signIn.sendEmailLink` (trooth.co's magic link), `linkExpiredFor` from the expired-link redirect, and `passkeyOffer.save` (worker-f's passkey registration) only on the first visit after an email link.
5. **Links**: `help`, `monitoring`, `handoff` (the signed developer handoff that expires in 7 days), `keys` (the key-binding panel), and `install` by `guide_id`: the Deploy to Cloudflare and Add to Vercel buttons, the WordPress plugin download, the Fastly, Akamai and Gcore packages, the nginx and Apache files, and the Shopify app listing. The Shopify app does not exist yet (`adapters/head-tag` covers Shopify today); until it does, point `shopify-app` at the head-tag guide. Defaults point at `https://trooth.co/docs/semanto/install/<guide_id>` and `/dashboard/semanto/*`, which are placeholders.
6. **Domain Connect return**: pass `domainConnectDeclined` when the provider redirects back with `error=access_denied`. `domain_connect_url` is never present until providers onboard the template.
7. **Classes**: everything used exists in trooth-web's globals (`text-text-*`, `text-ink-emphasis`, `bg-surface-*`, `border-hairline`, `bg-hairline`, `accent-text-primary`, `btn-primary`, `btn-secondary`, `btn-ghost`) plus Tailwind built-ins and one arbitrary value (`focus-visible:outline-[#1A73E8]`). Do not copy `harness/` or `web/types/`.
8. **Route**: `/dashboard/semanto/setup`, the page every Semanto email links to (Stripe's refresh pattern), replacing or embedding `semanto-setup-tracker.tsx`, whose six steps are the same six screens.
