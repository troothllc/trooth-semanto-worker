# Passkey signing

## The problem this fixes

The setup wizard said "Sign with my passkey" and the docs said a hosted company key is released only after a fresh WebAuthn assertion. The Worker checked no passkey at all: `POST /os/semanto/{id}/sign` signed with the hosted key on the workspace session alone, and the wizard fell back to the version's root hash as the WebAuthn challenge (a value anyone can compute, so an assertion over it proves nothing fresh). The label was an overclaim and the control was weak.

Now the hosted key is released only after this Worker has checked a passkey assertion made over a single-use challenge it issued for the exact version and root hash being signed. The label is true.

## Requirements covered

1. Registration: `passkeys/options` and `passkeys` exactly as asked (rp id from config, default `trooth.co`; rp name `Trooth`; 32-byte per-user handle in D1; 32-byte challenge, 5-minute TTL, single use; attestation `none`; ES256, EdDSA, RS256; resident key preferred, user verification required; the clientDataJSON, attestationObject and authenticatorData checks; storage per migration 0006).
2. Authentication for signing: `sign/options` bound to version and root hash; `sign` requires the assertion for hosted custody and checks type, challenge (consumed), origin, rpIdHash, UP, UV, the signature per algorithm, the sign count, and owner or admin; then the key is released; the approval record and the `authorized_by` entry carry the passkey; the two-officer rule counts distinct users with assertions for the same root hash; customer custody unchanged; plain problems for no passkey, expired challenge, wrong origin and cancelled.
3. Wizard: `sign/options` then `navigator.credentials.get` then `sign`; the "Add a passkey" step through `passkeys/options` and `navigator.credentials.create`; `has_passkey` in the setup state; the root-hash fallback removed; docs updated.
4. `Trooth-Request-Id` in `EXPOSED_HEADERS` and on every response.
5. Tests, including the Playwright harness.

## Deviations, on purpose

- **`checked_at`, not `verified_at`.** House rule 2 bans the past participle of "verify" in code, docs and tests. The approval record holds `{ credential_id, user_id, user_handle, checked_at }`; the header entry holds `{ credential_id, user_handle, checked_at }`.
- **One added field in `src/core/semanto.ts`** (allowed by the agent brief as a small export change). The exact diff:

  ```diff
  -  authorized_by?: { role: "OOR" | "ECR" | "owner" | "admin"; name?: string; credential?: string }[];
  +  authorized_by?: { role: "OOR" | "ECR" | "owner" | "admin"; name?: string; credential?: string; /** Hosted custody: the passkey assertion that released the key (W3C WebAuthn Level 3, 7.2). */ passkey?: { credential_id: string; /** The random per-person WebAuthn user handle (base64url), never an account id. */ user_handle: string; checked_at: string } }[];
  ```

  The field is optional and sits inside the signed header, so the company signature covers it. The verifier kits read headers as canonical JSON and need no change; their tests pass unchanged.
- **`src/index.ts` and `src/env.ts` were touched** to pass the rp id and the development switch to the pipeline. `wrangler.toml` was not touched: the default rp id is `trooth.co`.

## Founder steps and open points

1. **Apply migration 0006** to the production D1 database (`wrangler d1 migrations apply trooth_semanto --env production --remote`) before deploying this build. Without it, the passkey routes and every sign answer 500.
2. **CORS on `/os`** now answers `Access-Control-Allow-Origin` with the caller's origin when it is `https://trooth.co` or `https://www.trooth.co` (and `http://localhost` on any port only in development), else `https://trooth.co`, always with `Vary: Origin` (`dashboardOriginFor` in `src/serve/routes.ts`, `RouteDeps.dashboardOrigins`, set in `src/index.ts`). For a staging host, set `WEBAUTHN_RP_ID`, and add its origin to both `webauthnConfig` and `dashboardOrigins`.
3. **No worker-f id in the public header.** `authorized_by[].passkey` carries `user_handle`, the random 32-byte WebAuthn user handle (base64url) kept per person in `semanto_passkey_users`, never the worker-f user id. The internal `user_id` stays only in the D1 approval record (`semanto_authorizations.passkey_json`), where the two-officer rule counts distinct users. Tests check the header contains no user id. The verifier kits do not read the field, so they needed no change.
4. **Existing companies with hosted keys** cannot sign until each signer adds a passkey. Approvals recorded before this change have no passkey and no longer count for hosted custody.
5. **The counter write is conditional and atomic.** `touchPasskey` is one statement, `UPDATE semanto_passkeys SET sign_count = ?2, backed_up = ?3, last_used_at = ?4 WHERE credential_id = ?1 AND (sign_count < ?2 OR (sign_count = 0 AND ?2 = 0)) RETURNING credential_id`; no row returned means another assertion at that count was used first, and the sign is refused with `passkey_counter` (a possible copy). The in-memory store checks and writes with no await between. A test sends two concurrent assertions at the same count over two challenges: exactly one signs. Authenticators that keep the count at zero (allowed by WebAuthn, section 6.1.1) cannot be told apart this way; for them the single-use challenge is the guard.
6. The Screen A passkey offer after an email sign-in is worker-f's sign-in passkey and is unchanged; it is a different credential from the signing passkey.
